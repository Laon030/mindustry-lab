# Dual-LLM Autonomous Duel Demo v0

Updated: 2026-10-07 (Asia/Seoul)

This is a weekend demonstration milestone, separate from the logistics v1 and Memory Contract v2 research. Its result must not be used as evidence about scratchpad effectiveness. Development is gated: scripted combat and human GUI confirmation precede the coordinator, model calls, economy, production, and optional capture/upgrade work.

## Gate 1 — scripted combat proof passed; next Gate 2

**The Gate 1 acceptance condition—actual damage, death/removal, and a detected winner—passed in headless runtime and human GUI unit-combat observation.** The isolated runtime uses the Java 17 v159.7 dedicated server and the existing AgentBridge JAR. The server is hosted on the built-in `Islands` sandbox map. A small open area around tile `(159,72)` is used as a combat arena. Before combat, the fixture sets `pvp=true`, `pvpAutoPause=false`, `unitCapVariable=false`, `unitCap=10`, `infiniteResources=false`, and `instantBuild=false`. The cap override is necessary because this built-in map has no Crux core: with the default variable cap, a spawned Crux Dagger is removed immediately. This is a **pre-match fixture rule**, not unit production or a match action. The server's separate `autoPause` setting is also off for headless execution. The tested forces were intentionally 2-vs-1 to avoid the earlier equal-force mutual-elimination draw; this is not a balanced duel result.

The fixture creates Sharded and Crux Daggers before the match, then orders both sides through the vanilla `InputHandler.commandUnits` attack-target path using team-matched server-side `Player` objects. In the headless 2-vs-1 run, the Sharded Daggers moved and fought, one Sharded Dagger fell to 42/150 HP, the Crux Dagger fell below zero HP and `isAdded()` became false, while both Sharded Daggers remained in `Groups.unit`. `UnitDamageEvent` and `UnitDestroyEvent` appeared in the server log. A subsequent roster query found no Crux Dagger in `Groups.unit` and computed registered-force survivors A=2, B=0, winner=Sharded. This is a fixture-level winner calculation, not a native core-destruction `GameOverEvent`. An earlier 2-vs-2 run produced casualties on both sides and no surviving registered combat force on either side; that result is a **draw**, not a win. No HP edits, match-time teleport, or forced kill were used.

The current proof does **not** establish a balanced two-core map or a full PvP match. It establishes normal scripted unit combat and lifecycle in the tested fixture. The user personally confirmed movement, firing/combat, one death, and disappearance in the v159.7 CLIENT after the scripted orders. The 2-vs-1 fixture has already finished; its GUI evidence is reported below. A symmetric two-core match and native game-over outcome remain unverified.

The Gate 1 winner contract for this fixture is based only on the registered combat-force IDs: one team wins when it has at least one living, added registered unit and the opposing team has none; zero survivors on both sides is a draw. Other map units, including the core-associated Sharded unit, are excluded. Death is counted only after the game entity is removed, not from HTTP command acceptance or a negative HP value alone.
